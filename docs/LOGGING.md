# 日志与持久化

本文说明本项目的日志设计与**持久化策略**（保留多久、放在哪、什么时候会被清掉、
什么内容绝不能写进去），以及出问题时怎么用。

---

## 一、设计目标

日志的唯一目的是：**出事之后，证据还在。**

此前实现有三个致命问题，都直接导致过「查不出原因」：

| 问题 | 旧行为 | 后果 |
|---|---|---|
| **每次启动清空日志** | `open('fasterwhispergui.log', 'w')` | 重新启动复现问题的瞬间，**上一次运行的记录正好被抹掉** |
| **报错凭空消失** | 没有装任何全局异常钩子 | Qt 调用 `QThread.run()` 抛异常时只打一行提示、不带 traceback；叠加 stdout/stderr 重定向后信息彻底丢失 |
| **路径依赖工作目录** | 全是 `./xxx.log` | 从快捷方式启动就写到别处去了，用户找不到 |

## 二、文件布局

```
<程序目录>/logs/
├── app-20260928-021527.log     本次运行的完整日志（永不覆盖）
├── fw-20260928-021527.log      faster-whisper 库自身的日志（崩溃时对照）
├── latest.log                  最近一次运行（固定路径，方便让用户直接发出来）
└── diagnostics-20260928-021600.zip   可选：导出给维护者的诊断包
```

**命名**：`app-<YYYYMMDD-HHMMSS>.log` / `fw-<时间戳>.log`，时间戳是**进程启动时刻**。
同一个时间戳的 `app-*` 与 `fw-*` 属于同一次运行。

**目录选择**（按顺序，用真实写文件验证，不靠 `os.access` —— 它在 Windows 上不可靠）：

1. `<程序目录>/logs`
2. `%LOCALAPPDATA%/faster-whisper-GUI/logs`（程序装在只读位置时）
3. 系统临时目录（最后一档）

## 三、持久化策略

### 保留多少

**保留最近 20 次运行**，更早的在下次启动时删除。`latest.log` 永远不删。

只删自己生成的 `app-*.log` / `fw-*.log`；其它文件一律不动 —— 用户手工放进目录的
东西不能被误删。

### 磁盘占用

实测：一次 18 分钟音频的转写约产生 **28 KB** 应用日志。按 20 次保留估算：

```
20 × (28 KB + 少量 fw 日志) ≈ 1 MB 量级
```

**不需要按大小轮转**。选择「每次运行一个文件」而不是 `RotatingFileHandler`，是因为
排查时需要明确知道「这是哪一次运行」，轮转文件混在一起反而不好读。

### 为什么同时保留 `latest.log`

支持场景下最省事的说法是「把 latest.log 发我」。用户不需要理解目录结构，
也不需要找带时间戳的文件。代价是一次日志写两份（28 KB，可忽略）。

### 敏感信息

- **诊断包不含配置文件**。`fasterWhisperGUIConfig.json` 里存着 HuggingFace token，
  打包时必须排除（`exportDiagnostics()` 里显式只收日志与环境快照）。
- 日志里会记录模型路径、工作目录、用户名（体现在路径中）。这是排查必需的信息，
  但对外分享前应当知道这一点。
- 环境快照只读环境变量，**不做任何网络请求**，也不导入 `ctranslate2`
  （避免为了打印一行版本号而提前加载 DLL）。

### 卸载与清理

日志位于程序目录下的 `logs/`（或 `%LOCALAPPDATA%`），不会写到系统其它位置。
直接删除 `logs/` 目录即可；程序下次启动会重建。

## 四、一条管道、多个出口

```
print() ─┐
第三方库 ─┤→ LoggingStream → logging ─┬→ FileHandler  app-*.log   (DEBUG 起)
异常钩子 ─┤                          ├→ FileHandler  latest.log   (DEBUG 起)
Qt 消息  ─┘                          ├→ FileHandler  fw-*.log     (仅 faster_whisper)
                                     └→ CallbackHandler → 界面文本框 (INFO 起)
```

关键点：**文件那一份永远不经过界面**。旧实现把 `sys.stdout` 换成一个 Qt 信号对象，
于是「信号没派发出去」等于「日志里也什么都没有」—— 界面卡住时连日志都断了，
最难查的正是这种状态。

`print()` 由 `LoggingStream` 在**流**这一层接管，因此天然正确处理多参数、`sep`、
`end` 以及第三方库直接 `write()` 的情况。调用点也已脚本化改写为带级别的
`log.info/...`（一次性迁移脚本已归档，见 [清理记录](CLEANUP.md)）。

## 五、级别约定

写代码时请遵守，否则日志会退化成噪声：

| 级别 | 用途 | 例子 |
|---|---|---|
| `DEBUG` | 库内部细节、DLL 注册、参数快照 | ROCm DLL 目录列表 |
| `INFO` | 阶段标记、每一段转写结果 | `[12.34s --> 15.67s] 转写内容` |
| `WARNING` | **可恢复**的异常 | 单个文件失败、对齐退回 CPU、配置节缺失 |
| `ERROR` | **用户可见**的失败 | 写字幕失败、模型加载失败 |
| `CRITICAL` | 未捕获异常、线程崩溃、进程级故障 | 完整 traceback |

**两条硬规则：**

1. **界面看到的那条错误，和日志里那条，必须是同一条。** 旧实现弹「分离失败」
   而日志里什么都没有；线程崩溃则反过来日志有 traceback、界面不弹。
2. **绝不静默吞异常。** 确实无害的（清理路径上的 `del`）也要 `log.debug` 一句。
   本项目原有 78 个 `except` 中有 47 个是静默的，其中 4 个直接造成用户的配置被
   重置后写回文件。

## 六、出问题时怎么用

1. **程序起不来 / 行为异常** → 设置页「日志文件 → 打开」，看 `app-*.log` 尾部。
2. **转写崩溃** → 设置页「faster-whisper 日志文件 → 打开」，看 `fw-*.log`。
3. **要发给维护者** → 设置页「日志目录 → 导出诊断包」，把生成的 zip 发出去即可。
4. **想复现上一次的问题** → 上一次的 `app-<时间戳>.log` 还在（这正是本次改造的核心）。

环境快照写在每个日志文件的开头，包含 Python/依赖版本、内存、工作目录、ROCm 环境变量，
所以**用户发一份日志通常就够了**，不必来回追问环境。

### 一个必须知道的坑

当前应用使用普通导入加载 `logging_setup`。测试或外部诊断工具按文件路径加载时，
仍可能产生两份模块实例，因此继续保留进程级幂等保护。

两份实例各自的 `_configured` 都是 `False`，第二次 `setupLogging()` 会用
`mode="w"` 把刚写好的日志清空（**实测发生过**：启动日志先有 177 字节，随后变 0）。

因此「已配置」状态挂在 **root logger 的属性**上（进程内唯一），而不是模块变量。
`src/project_tools/check_logging.py` 第 11 组测试专门守着这一点。
